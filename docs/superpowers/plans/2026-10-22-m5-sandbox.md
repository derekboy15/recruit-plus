# Milestone 5 (Sandbox) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A two-player, pass-and-play 40k game on one device at `/play`, played on a real-scale PixiJS board, with every core rule decided by `@recruit/engine`, faction rules assisted (ability and stratagem lists, one-tap modifiers, manual toolkit), and saved, resumable games.

**Architecture:**
- **The engine is the judge.** The UI never decides a rule. Every player action becomes one engine `Command`, sent with `dispatch(record, cmd)`.
  - An accepted command replaces the record, and the game is saved.
  - A rejected command shows the engine's `Problem.message` (plain English, with its rule tag), and nothing changes.
  - **Live feedback uses dry runs.** `dispatch` is pure, so the UI can check a planned move or deployment by dispatching it and throwing the result away. It does this on drop, never on every pointer move, to keep big armies fast. The "Confirm" button is enabled only when the dry run is accepted. That is how the hard limits (Move, Advance, coherency, engagement range) are enforced.
- **Three layers in `apps/web/src/play/`:**
  - **Pure logic:** missions, terrain layouts, setup building, camera, gestures, formation, scene building, the plan reducer, stratagem and ability relevance, and hints. All of it is unit-tested.
  - **Board renderer:** `BoardCanvas` draws a `BoardScene` (a plain description) through a `SceneRenderer` interface. The real renderer is PixiJS and loads lazily. Tests inject a fake renderer, so Pixi never loads in jsdom.
  - **React panels:** one panel per phase and step, plus pending-roll, reaction and placement panels, chosen from `currentStep(state)`.
- **The game doc.** A saved game is a storage doc of kind `'game'`. It holds the engine `GameRecord` (plain JSON) and some meta: the armies' catalogue slugs (for abilities), the hints setting, and the layout and mission ids. It saves 300 ms after each accepted command, and at once when the page is hidden. On load, `validateRecord` and `loadGame` guard old or damaged saves.
- **Missions behind a small interface.** `SandboxMission` gives the deployment zones, edges and objectives for a board. This milestone ships one "Practice" layout, labelled as not an official mission. Milestone 7 adds its Arks of Omen and Core Book missions by registering a provider (`registerMissionProvider`). No other code changes.

**Tech Stack:** React 19, TypeScript 7, Vite 8, Vitest 5 with Testing Library, Playwright 1.64 (all unchanged); `pixi.js@8.22.0` (new, exact pin); workspace `@recruit/engine` (new dependency of `apps/web`).

## Global Constraints
- **Wrong rules are the worst failure.** The UI never decides a rule. It never filters out a legal choice, and never offers an option it can't check, without the engine confirming. Eligibility lists (`eligibleUnits`, `fightOrder`, `needsMoraleTest`) are hints for what to show first. The engine's answer to the command is final.
- **No engine changes are planned.** If the UI exposes an engine bug, fix it test-first in `packages/engine` (test title with a citation tag), in its own commit, and report it in the hand-over notes.
- **Phones first.** It must work at 375×812. Every tappable control is at least 44 px tall (`var(--touch)`), and there is no sideways page scroll (the board pans inside its own box). Touch hit-testing on the board uses a 22 px slop around bases.
- **Real scale.** Board sizes come from `BOARD_SIZES` (Combat Patrol 44"×30", Incursion and Strike Force 44"×60", Onslaught 44"×90"). Bases are the datasheet `base` shapes, drawn with `polygonOf`. World units are inches. Player A's edge is south (`y = 0`, bottom of the screen); Player B's is north.
- **Plain English.** Rules text defaults to plain English. The existing `WordingProvider` and `WordingToggle` switch to official wording. UI copy names things the way the Rules Reference does ("Normal Move", "Advance", "Fall Back", "Remain Stationary", "Engagement Range", "Command Re-roll").
- **Pass-and-play.** Whenever the player who must act next (`currentStep(state).actingPlayer`) changes, a full-panel "Pass the device to ⟨army name⟩" screen appears, with one button, "I'm ⟨army name⟩". It can be turned off in the game menu.
- **Every manual adjustment is a logged, undoable engine command** (R-19). Undo calls the engine's `undo`, which never reaches back past the start of the current phase or step, and shows its refusal message.
- **Bundle:** the engine, Pixi and the play pages load only from the `/play` routes (`lazy`). Pixi loads only when a board mounts.
- **Test-only hooks:** `window.__sandbox` (model screen positions and the state) exists only when `import.meta.env.DEV` is true. E2E uses it to find models on the canvas.
- **Copy rules from earlier milestones apply:** no BattleScribe or engine jargon ("selection", "event", "batch", "command") in user-facing text.

## Review Focus
1. **Tiny bases on a phone.** A 25 mm base on a fitted 44" board at 375 px wide is about 8 px. A tap or drag within 22 px of a base must still pick it, the nearest base winning. A drag that starts on empty board must pan. Tests: Task 6 `hitTest` slop and nearest-wins tests; Task 5 gesture "down on empty then move pans".
2. **Resuming mid-decision.** A game saved while a roll window, a reaction or a passenger placement was open must reopen on that same panel, with the same dice, after a reload. Test: Task 9 "a game saved with a roll window open reopens on the roll".
3. **Saved games the engine can't read** (made by a newer version, damaged, or JSON from elsewhere): the game screen shows the engine's `EngineLoadError` message and offers "Delete this game"; it never crashes. Tests: Task 3 `openGameDoc` returns the error; Task 9 renders it.
4. **Lists that don't muster cleanly.** A list may have no units, units the engine can't match, or unmatched weapons. Setup shows each problem in plain English. It refuses to start when an army has no units, and lets the game start (with the problems listed) when only some weapons or models are unmatched. The same list chosen for both players works, because unit ids get a player prefix. Tests: Task 3 `musterArmy` and `buildGameSetup`; Task 4 renders the problems.
5. **Vehicles and other non-round bases.** Oval and rectangular bases must be turnable, or they can't fit through gaps or be placed wholly in a zone. The selected model gets "Turn left 15°" and "Turn right 15°" buttons that rotate its planned `rot`, and the dry run judges the rotated footprint. Tests: Task 6 `planReducer` rotate; Task 11 the rotate buttons dispatch a move with the new `rot`.

- **Practice layout values:**
  - **Zones:** strips along each player's edge, `depth = min(12, (h - 12) / 2)`. That is 9" on a 30" board and 12" on the others. A's zone is `y ∈ [0, depth]` (south); B's is `y ∈ [h - depth, h]` (north). Both span the full width.
  - **Objectives** (ids `'1'`, `'2'` and so on):
    - Combat Patrol (4): `(w/4, h/2)`, `(3w/4, h/2)`, `(w/2, depth/2)` and `(w/2, h - depth/2)`.
    - Incursion and Strike Force (5): those four plus the centre `(w/2, h/2)`.
    - Onslaught (6): those five plus `(w/2, h/2 ± h/6)`, replacing the centre. That's `(w/4, h/2)`, `(3w/4, h/2)`, `(w/2, h/3)`, `(w/2, 2h/3)` and the two zone objectives.
  - **Description:** "A simple practice layout for the sandbox: deploy along your own edge, objectives in the middle and in each deployment zone. It isn't an official mission; primary objectives score as in the battle size's mission pack."
- **Layouts:** all three are point-symmetric about the centre (each feature has a twin rotated 180°). Footprints are given as fractions of `w` and `h`, so they fit every board, and nothing lies inside a deployment zone's first 3".
  - `open` ("Open field"): 2 craters (`TERRAIN_PRESETS.craters`, height 0.5).
  - `city` ("Ruined city"): 4 ruins (`ruins`, obscuring, height 6) and 2 craters.
  - `mixed` ("Ruins and woods"): 2 ruins (height 6), 2 dense woods (`woods`, height 4) and 2 craters.
  - Feature names: "Ruins", "Woods", "Crater".

  ```ts
  export interface Camera { scale: number; x: number; y: number }   // screen px of world (0, board.h); px per inch

    | { kind: 'drag'; id: number; modelId: string }
    | { kind: 'pinch'; a: number; b: number; pts: Record<number, Pt>; lastDist: number; lastMid: Pt };
  export type GestureOut =
    | { type: 'tap'; at: Pt; modelId: string | null }
    | { type: 'drag-start' | 'drag-move' | 'drag-end'; modelId: string; at: Pt }
    | { type: 'drag-cancel'; modelId: string }
    | { type: 'pan'; dx: number; dy: number }
    | { type: 'zoom'; factor: number; at: Pt };
  export interface GestureEnv { hit(pt: Pt): string | null; canDrag(modelId: string): boolean }
  export const TAP_SLOP_PX = 8;
  export function reduceGesture(s: GestureState, e: PointerEv, env: GestureEnv): { state: GestureState; out: GestureOut[] };
  ```
- **Gesture rules:**
  - **down:** goes to `press`, with the hit model.
  - **move beyond 8 px from `press`:**
    - on a draggable model, it becomes `drag` and emits `drag-start` then `drag-move`;
    - otherwise it becomes `pan`.
  - **up within 8 px:** a `tap`.
  - **A second down:** goes to `pinch` from any state. A drag in progress emits `drag-cancel` first.
  - **During a pinch:** `zoom` with `factor = dist / lastDist` about the midpoint, plus `pan` by the midpoint's motion.
  - **up during a pinch:** goes to `idle`. The remaining finger does nothing until it lifts.
  - **cancel:** goes to `idle`. A drag in progress emits `drag-cancel`.
  - The wheel is handled by `BoardCanvas` as `zoom` (`factor = 1.1 ** (−deltaY / 100)`).
